## 1. 目标架构(同机双域)

```
                同一台服务器(Debian,Nginx 单点反代)
 ┌──────────────────────────────┬──────────────────────────────┐
 │  jerseyshelf.com(主店)      │  <JERSEYDOCK 域名>(卫星店)  │
 │  Node HTTP :3001(systemd)   │  KITVAULT web :3000          │
 │  唯一上架入口(PIM)          │  KITVAULT admin :3002        │
 │  商品/分类/定制/翻译/推荐    │  (admin 端口从 3001 改开,   │
 │  批量导入 → 写库即出同步流   │   避免与主店 3001 冲突)      │
 └──────────────┬───────────────┴──────────────┬───────────────┘
                │  共享内容寻址图库(方案B)     │
                └──────────→  /srv/media/  ←───┘
                       文件名 = SHA-256,两店只登记不复制
                商品同步:单向拉取  主站 /api/sync/catalog → KITVAULT 定时 poll
                订单/支付/OMS/客户/售后:两店完全独立,各收各款各履各约
```

要点:

- **图库方案 B(共享目录)**:主站 media 表本就是 SHA-256 内容寻址、文件名即哈希,零改造;KITVAULT 侧新增 `/media/[hash]` 只读路由指向共享目录(现有 `/assets`、`/imports` 路由保留服务旧数据集图片)。Nginx 对两店 server 块都加 `location /media/ { alias /srv/media/; }` 静态直出,Node 不经手,缓存头沿用 immutable。
- **商品主从**:主站唯一上架入口(后台编辑与批量导入都走同一写路径 → outbox 表 `catalog_changes`),KITVAULT 每 10 分钟 poll + 手动"立即同步",upsert 入本店库,本店差异只写 overrides(价格系数、上下架、文案、品牌名)。**同步的只是商品资料**(标题/描述/价格基准/分类/规格/定制模板/图片清单);**库存数量不参与同步**——两店库存各自独立管理,同一款在两店可售量互不影响(球衣类目通常不设严格库存,如将来需要防超卖再加同步开关)。
- **运营零共享**:两店各自的前台用户体系、后台账号、订单库、支付收款、OMS/物流商账号与 17TRACK key、售后与回款,全部独立运行互不相通。开发期若临时共用第三方测试凭据,只是为了省配置,不代表运营共享,联调前应分开。
- **同机部署形态**:DNS 两条 A 记录 → 同一 IP;KITVAULT 用 `output: 'standalone'` 产物以 systemd/pm2 跑 `next start`;出网走既有 `HTTP(S)_PROXY` 配置。

## 2. KITVAULT 侧工作清单(本项目要做的活)

### S0 — JSONL 迁真库(前置,约 2 人日,可立即开工,不依赖主站)

主站方案 2.4 的判断成立:往 JSONL 做事务性 upsert 不可靠,这一步不可省。

1. Prisma provider 先落 **SQLite**(主站同机同盘,零外部依赖;PostgreSQL 待将来多机时再切),schema 沿用 `packages/db/prisma/schema.prisma`,补 `SyncCursor`、`CatalogOverride` 两个 model。
2. 迁移脚本:`data/orders.jsonl`、`users.jsonl`、`events.logl`、`contacts.jsonl`、`admin/*.json`(admins/settings/overrides/imported-products/import-batches/followups/media/audit)→ 各表;dry-run 对照行数;旧文件只读保留一个版本周期。
3. 改造数据访问层:所有 `fs` 读写文件的工具(`lib/orders.ts`、`lib/users.ts`、`lib/settings.ts` 等)替换为 Prisma 调用;**商品读路径同步改造**——前台/后台从"内存数据集数组 + overrides 叠加"改为"查库 + overrides 叠加",这是 KITVAULT 侧最大单点工程。`packages/shared` 数据集降级为初始化种子(首库导入 3,736 件,随后以主站同步全量对齐)。
4. 埋点 `events.logl` 可保持文件追加(只写日志,无事务需求),或一并入表,取实现成本最低者。

### S2 — 同步消费端(约 1.5 人日,依赖主站 S1 出口)

1. **拉取器** `apps/web/src/lib/catalog-sync.ts` + `app/api/sync/pull/route.ts`(手动触发,admin 权限)与 instrumentation 定时器(10 分钟):`GET <主站>/api/sync/catalog?cursor=<seq>&limit=200`,令牌走本店 settings(主站令牌封存在其 settings `sync`,两侧同源规则:密钥文件成套备份)。
2. **落库语义**:upsert 按 slug 对齐(首连全量时如遇 KITVAULT 既有 handle 与主站 slug 不一致的存量商品,以主站为准、旧 handle 记入映射表防 SEO 死链);`op=delete` 的 tombstone → 本店 `status=archived`(软删,不物理删);商品包带内容哈希,未变跳过,重复投递幂等。
3. **媒体处理**:每条媒体 `{hash, ext, bytes, url}` —— 先查共享目录命中即登记(零拷贝);未命中按 URL 拉取、以 `hash` 命名落盘到共享目录、`bytes` 校验后登记。URL 统一重写为本店 `/media/<hash>` 形式。
4. **overrides 生效**:价格 = 同步基准价 × 本店系数;上下架、标题文案、定制开关可本店覆盖;两店同货不同价、不同品牌(JERSEYDOCK vs jerseyshelf)由此实现。
5. **联动**:同步落库后触发本店图搜增量 reindex(复用 `/api/search/reindex` 增量通道);商品翻译不依赖主站——只同步原文,本店 29 语 MT 懒翻管线照常工作(解耦,主站翻译体系故障不影响本店)。
6. **后台页** `apps/admin/src/app/sync/page.tsx`:cursor 位置、最近批次、失败明细、"立即同步"与"全量重建"按钮(权限 `settings.edit`)。

### 安全员整改(约 1 人日,与 S0 并行,独立上线)

1. **Stripe webhook**:去掉 `if (secret)` 短路——未配置 webhookSecret 时返回 400 拒绝处理并记日志(回归主站方案阶段的修正);PayPal webhook 同样检查(`apps/web/src/app/api/payment/webhook/paypal/route.ts`)。
2. **Google id_token 验签**:拉取 `googleapis.com/oauth2/v3/certs` JWKS,`crypto.createVerify('RSA-SHA256')` 验签 + 校验 `iss/aud/exp/nonce`。
3. OMS base_url 增加 https 偏好(现默认 `http://oms.cfky888.com:7772` 明文;短期无法改服务端则至少后台标红警示)。

## 4. 上轮对比结论的修正

上一版方案中"按球衣项目移植到 KITVAULT"的 P0–P2 清单,在新方向下重新归类:

- **仍然有效(KITVAULT 本店自建)**:售后体系(最大缺口,S0 后开工)、COD 回款账本、订单待办体系、客户任务自动化、Meta Pixel、结账省市联动+立即购买+满减配置化——这些是卫星店自己订单运营所需,主站的功能帮不到本店订单。
- **转为主站职责,KITVAULT 不再排期**:翻译 Provider 接力后台化(KITVAULT 保持免费轮换即可)、博客/首页模块(内容营销在主店做)。
- **反向修正**:安全整改项(支付 webhook 验签、Google id_token)从"主站重写时修正"变为"KITVAULT 立即修"——本店在线上跑着的就是带缺陷的代码,不能等。
- **维持不变**:以图搜图保留 KITVAULT 方案(CLIP+视觉大模型兜底),主站方案 #9 也是把这套思路接回它的 Python 引擎后面,方向一致。
