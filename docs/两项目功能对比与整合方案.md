# 两项目功能对比与整合方案

> ⚠️ **本文档的整合方向已作废**(2026-10-24):实际方向已定为"球衣独立站为主店、KITVAULT 为卫星店"的双店协同架构,现行方案见《双店协同整合方案.md》。本文第 1 节的功能优劣判定仍可作参考。

> 2026-10-24 生成。对比对象:`D:\独立站`(KITVAULT,Next.js 15 monorepo,本文档所在项目)与 `D:\球衣独立站`(jerseyshelf.com,Node HTTP + SQLite,已上线生产)。
> 结论性文档:逐功能域判定优劣,并给出"整合最优方案进 KITVAULT"的路线图。功能清点依据两边代码与文档(球衣独立站 README/docs + 22 个测试文件;KITVAULT apps/packages/docs)。

## 0. 总判定

**以 KITVAULT 为唯一前进代码库**,球衣独立站作为功能与数据模型的"参考实现库"。理由:

- KITVAULT 在四个关键现代化维度上领先且无法从球衣项目"补":在线支付(Stripe/PayPal/转账)、OMS API 自动履约(TWMS 自动推送/轨迹/面单)、RBAC 权限体系、现代前端与 SEO 管线(sitemap/robots/JSON-LD)。
- 球衣独立站领先的领域(COD 资金闭环、售后对账、客户跟进工作台、WhatsApp Cloud API、Meta Pixel、翻译运营、结账地址体验)全部是**业务流程与数据模型层面**的优势,可以在 KITVAULT 上重实现;且其 SQLite 迁移文件(001–025)就是现成的领域模型参考。
- 两边技术栈不兼容(零依赖 Node vs Next.js),移植 = 按模型重写,不是拷代码。

## 2. 整合路线图(建议优先级)

### P0 — 钱与货的闭环(直接影响能不能管好生意)
1. **售后体系移植**(判定 #5):Prisma/文件模型 + 订单详情"售后处理"分区 + 部分退货/入库/换补发/退款登记/差额对账。先写测试。
2. **COD 回款账本**(判定 #4):回款登记毛/费/净 + cod_events 留痕 + 多包裹代收限额 + 退回入库恢复库存,接在现有 10 状态推导之后。
3. **订单中心待办体系**(判定 #6):六项待办计数 + 详情分区重构,叠加在现有订单页。
4. **客户跟进任务自动化**(判定 #7):六类任务派生规则 + 分组筛选 + 导出。

### P1 — 增长与触达
5. **Meta Pixel + 同意管理**(判定 #8)。
6. **WhatsApp Cloud API**(判定 #9):配置页、模板队列、webhook。
7. **结账体验包**(判定 #12/#13/#14):省市联动+邮编规则、立即购买、满减可配置化。

### P2 — 运营配置化与内容
8. 推荐/最近浏览配置(#15)、翻译 Provider 接力后台化+密钥加密(#10)、博客/首页模块(#16)、流量统计卡(#17)、分类软删可恢复(参考球衣 collections)。

### 持续事项
- 每个域移植时同步补测试,向球衣站的验收纪律看齐。
- Prisma 迁移时吸收球衣 SQLite 迁移的域模型(尤其 019/023/024/025)。
- 本地搜图模型评估升级 SigLIP 2(#11)。

## 3. 风险与注意事项

- **移植是重写不是拷贝**:两边栈不同,球衣的 .mjs 业务代码只能作为流程与模型参考;其 SQLite 迁移 SQL 是最好的 schema 蓝本。
- **素材版权**:两站商品图同源于 chenyikan.shop 采集,KITVAULT README 已标注"正式上线需替换自有授权素材",整合不改变该约束。
- **OMS 明文 HTTP**(oms.cfky888.com:7772):非本对比新增问题,但整合期建议推动服务商上 HTTPS 或走代理隧道。
- **球衣站仍在生产运行**:整合期间两站并行,jerseyshelf.com 承接真实订单;KITVAULT 上线切换前不要关停,以球衣站的 COD 人工闭环作为过渡期兜底。
