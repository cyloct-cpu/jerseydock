# 订单管理页改造设计(COD 代收 + 款项筛选体系)

> 2026-10-24 · 配合 [oms-物流对接方案.md](./oms-物流对接方案.md) 第一期落地。
> 目标:① COD 订单走 OMS 代收费,回款状态在物流轨迹和订单列表中可见;② 一套筛选系统,一眼识别每单的钱在什么状态、货到了没付款是什么原因;③ 兼容后续「先支付后发货」模式。

---

## 0. 一个必须先讲清的事实:OMS 轨迹里没有"钱到账"事件

OMS 的轨迹接口(GetOrderTrack)只有**物流事件**(已签收/拒收/派送异常/丢件…),没有「代收款已到账」的实时回调和查询接口(现有 API 目录中无结算类接口)。所以 COD 的钱有两个阶段:

1. **签收/拒收** —— 轨迹能自动告诉我们,系统据此自动归类;
2. **回款到账** —— 服务商按结算周期打款(对账单),**只能靠人工核对后标记**。

因此系统把"货到了还没付款"自动拆成几种原因,唯独「已签收等回款」这种正常账期状态需要你定期和账单核对后点一下「标记回款」(或后续做对账单导入)。这一点决定了下面的整个设计。

## 1. 统一「款项状态」模型(核心)

新增一个**推导函数** `moneyStateOf(order)`,综合 支付方式 + paymentStatus + 履约状态 + 最新轨迹 + 回款标记,算出 10 种状态。订单数据不迁移,老数据自动适配:

| moneyState | 显示 | 判定规则 | 含义 |
|---|---|---|---|
| `pending_online` | 🔴 待支付 | method=online & paymentStatus=pending | 线上下单未付款(先付后发模式:不推送 OMS) |
| `transfer_waiting` | 🟠 转账待确认 | method=transfer & pending | 等你确认收款 |
| `prepaid` | 🟢 已预付 | (online/transfer) & paid | 先付款后发货,已收全款 |
| `cod_pending` | ⚪ COD待推送 | COD & unfulfilled & 未推 OMS | 已下单待推服务商 |
| `cod_push_failed` | 🔴 推送失败 | oms.pushError 存在 | 推 OMS 被拒,显示原因 |
| `cod_transit` | 🔵 代收在途 | COD & shipped/in_transit | 包裹运输中,钱由快递员代收 |
| `cod_signed` | 🟡 已签收·待回款 | COD & delivered & 无 codConfirmedAt | **货到了,钱还没确认到账**(正常账期) |
| `cod_refused` | ❌ 拒收·未收款 | COD & exception & 轨迹含 拒收/退件 | 客户拒收,货退回,**收不到款** |
| `cod_exception` | ❌ 异常·未收款 | COD & exception & 其他轨迹 | 派送异常/丢件/销毁,未妥投未收款 |
| `collected` | 🟢 已回款 | COD & 有 codConfirmedAt | 已核对到账 |
| `refunded` | ⚫ 已退款 | paymentStatus=refunded | — |

**「货到了还没付款」的原因归因表**(列表行内直接显示):

| 系统检测 | 行内显示的原因 |
|---|---|
| 轨迹已签收 ≤14 天,未标记回款 | 「10-20 已签收,代收款在服务商结算周期内」 |
| 轨迹已签收 >14 天,未标记回款 | 「已签收超 14 天未回款,建议与服务商对账」⚠ |
| 轨迹=拒收/退件中 | 「客户拒收,包裹退回中,款项未收」 |
| 轨迹=派送异常/待取件超时 | 「派送异常,未妥投未收款,需联系客户或服务商」 |
| 轨迹=丢件/销毁 | 「包裹丢失/销毁,款项未收,需向服务商索赔」 |
| 在线支付 pending 超 48h | 「客户下单后一直未完成线上支付」 |

## 2. 数据层改动(全部向后兼容)

订单对象新增可选字段(无字段=老数据,按规则推导):

```ts
codConfirmedAt?: string      // 回款确认时间(setCodCollected 写入,同时 paymentStatus→paid)
oms?: {                      // 方案文档已定义,补充两个字段:
  ...
  pushError?: string         // 推送失败原因
  lastTrackStatus?: string   // 最新轨迹中文状态,如「派送中」
  lastTrackAt?: string
}
```

新增 server actions(`apps/admin/src/lib/actions.ts`):
- `setCodCollected(orderNo)` —— 标记回款:写 codConfirmedAt、paymentStatus='paid'、追加轨迹事件「COD 回款确认 · $XX」、记审计日志;
- `setCodRefused(orderNo)` —— 人工标记拒收(轨迹缺失时兜底):fulfillmentStatus='exception' + 轨迹事件「人工标记拒收」;
- `retryOmsPush(orderNo)` —— 重试推送(重置队列状态)。

轨迹中体现 COD:签收时系统自动往 shipment.events 追加一条合成事件「包裹已签收 · COD 代收金额 $XX,待服务商回款」,轨迹时间轴(管理轨迹弹窗、前台客户页)即能看到钱的状态线;标记回款后再追加「COD 回款已确认」。

## 3. 页面布局改造(自上而下逐区块)

改造后整体结构:

```
┌ 页头:订单管理                    [同步OMS] [导出 CSV] ┐
├ 统计卡片条(新增,4 张,点击即筛选)                     ├
│  [COD待回款 $112 · 2单] [签收超7天未回款 1⚠]          │
│  [推送失败 1] [本月已回款 $350 · 3单]                 │
├ 快捷筛选条(新增,一排带数量的 chips,单选)              ├
│  (全部 5)(待处理 1)(代收在途 2)(待回款 1)           │
│  (未收款风险 1)(已收款 0)(已退款 1)                  │
├ 筛选工具栏(升级)                                    ├
│  搜索[单号/邮箱/姓名/快递单号] 款项状态[▼] 支付方式[▼]  │
│  履约状态[▼] 下单时间[▼] [筛选] [重置]                ├
├ 表格:□|订单号|时间|客户|商品|金额|款项|物流|操作        ├
└ 批量栏(升级) + 底部手工发货卡(保留,标注"兜底")        ┘
```

### 3.1 页头(右上角)

| 元素 | 说明 |
|---|---|
| `同步 OMS` 按钮(新增) | 手动触发一次轨迹/状态同步(admin 进程内 worker 正常每 30-60 分钟自动跑,这个用于急查单)。POST `/api/oms/track-sync`,完成后刷新页面并提示「已更新 N 单」 |

### 3.2 统计卡片条(新增,位于页头与快捷筛选之间)

4 张卡片,均为链接(点击=带预设筛选跳转):

| 卡片 | 数据来源 | 点击行为 |
|---|---|---|
| COD 待回款 `$112.00 · 2单` | moneyState=cod_signed 的单数与 totalUsd 合计 | 筛选到「待回款」 |
| 签收超 7 天未回款 `1单 ⚠` | cod_signed 且签收时间>7天 | 同上,列表内超期单置顶标红 |
| 推送失败 `1单` | oms.pushError 非空 | 筛选到推送失败 |
| 本月已回款 `$350 · 3单` | 本月 codConfirmedAt 的单 | 筛选已回款 |

### 3.3 快捷筛选条(新增)

一排 chips(纯链接,服务端筛选,保持现有 server component 架构):

`(全部 N) (待处理 N) (代收在途 N) (待回款 N) (未收款风险 N) (已收款 N) (已退款 N)`

- 待处理 = pending_online + transfer_waiting + cod_pending + cod_push_failed(**每天打开页面先看这一组**)
- 未收款风险 = cod_refused + cod_exception
- 已收款 = prepaid + collected
- 选中态高亮,URL 参数 `m=xxx`,与下面细筛可叠加

### 3.4 筛选工具栏(升级现有 4 控件 → 6 控件)

| 控件 | 现状 | 改造 |
|---|---|---|
| 搜索 | 订单号/邮箱/姓名 | 追加匹配 shipment.trackingNo、oms 单号 |
| 款项状态(替换原「支付状态」) | 5 个原生 paymentStatus | 按 §1 的 10 种 moneyState 出选项(全部/待支付/转账待确认/已预付/COD待推送/推送失败/代收在途/已签收待回款/拒收未收款/异常未收款/已回款/已退款) |
| 支付方式(新增) | 无 | 全部/货到付款 COD/在线支付/银行转账 —— 和款项状态正交,例如「COD × 已签收待回款」 |
| 履约状态 | 6 项 | 追加「待推送」「推送失败」两项(OMS) |
| 下单时间(新增) | 无 | 全部/近7天/近30天/近90天 |

### 3.5 表格列改造

**「支付」列 → 「款项」列**(名称改,内容两行):

```
[🟡 已签收·待回款]          ← moneyState 徽章(颜色见§1)
货到付款 $112.00            ← 支付方式 + 代收金额
10-20 已签收,等服务商回款    ← 原因行(§1 归因表)
[标记回款]                  ← 条件按钮,见下表
```

**「履约」列 → 「物流」列**:

```
[🔵 运输中]                 ← fulfillment 徽章(追加 待推送/推送失败 两种)
日本佐川 · 499606170114      ← OMS 渠道·单号(自动回填)
最新: 派送中 10-24 14:30     ← oms.lastTrackStatus(小字)
```

**「发货/操作」列 → 按状态显示不同按钮组**:

| 订单状态 | 显示按钮 | 功能 |
|---|---|---|
| 已推 OMS(有单号) | `管理轨迹` | 现有,弹轨迹时间轴(含 COD 合成事件) |
| | `客户链接 ↗` | 现有,客户免注册看单号+轨迹 |
| | `打印面单`(新增) | 打开本地留存的面单 PDF(`/api/oms/label?orderNo=`),无面单时置灰 |
| | `标记拒收`(仅 COD,低频) | 轨迹缺失时人工兜底 |
| 推送失败 | `重试推送`(新增,主按钮) | 调 retryOmsPush 重新入队,行内显示失败原因 |
| | `管理轨迹`/`客户链接`(灰态) | — |
| 未推送(cod_pending / prepaid 待发) | `推送 OMS`(新增,主按钮) | 手动立即推送(不等 worker 的每分钟轮询) |
| | 原手工发货表单(保留) | OMS 故障降级用,收起为「手工发货 ▾」折叠 |
| 全部 | `删除订单` | 现有 |

**「标记回款」按钮**(放在款项列,COD 且 cod_signed 时显示,是最常用的 COD 操作):点击 → 确认弹层「确认已收到 KV-XX 的代收款 $112?」→ setCodCollected → 款项徽章变 🟢已回款,轨迹追加回款事件。

### 3.6 批量栏(升级)

现有「删除选中」旁追加:
- `批量标记回款` —— 对勾选的 COD 已签收单批量 setCodCollected(对账日批量点);
- `批量推送` —— 对勾选的待推送/推送失败单批量入队。

### 3.7 底部「批量填物流单号」卡保留

标注「OMS 故障时手工兜底」,平时用不到。

## 4. 与「先支付后发货」模式的兼容

- 款项状态机天然支持:online 待支付 → 已预付(prepaid)→ 推送 OMS(COD 字段传 0);
- 触发规则在 worker 里按 paymentMethod 分流:online=支付回调后入队;cod=下单即入队(COD 金额=totalUsd);transfer=标记已支付时入队;
- 筛选系统不需要改:待支付/已预付都是现成选项;
- 将来若做「未付款拦截」(超48h自动取消),在统计卡「待支付」上加提醒即可,本期不做。

## 5. 联调确认项(影响 COD 字段)

1. COD 金额**币种**:OMS 的 COD 字段传什么币种(USD 还是目的国本币)?渠道不同可能不同,联调时用测试单确认(订单系统内部记账是 USD,推送时可能要按渠道汇率换算);
2. 哪些渠道支持代收(getShippingMethod 返回后确认,渠道名带「COD」的优先);
3. 服务商结算周期(回款预计延迟多少天,用于「签收超 N 天未回款」的提醒阈值,默认 14 天,settings 可配)。

## 6. 实施拆分(随第一期一起交付)

1. `lib/money-state.ts`:moneyStateOf + 归因文案(纯函数,页面/CSV/统计共用);
2. actions: setCodCollected / setCodRefused / retryOmsPush;
3. 页面改造:统计卡 + 快捷筛选 + 工具栏 6 控件 + 款项/物流/操作三列重构;
4. 导出 CSV(/api/export?type=orders)同步输出 moneyState 列;
5. 轨迹合成事件(签收→COD 待回款;标记回款→回款确认)。
